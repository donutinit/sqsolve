## Finding while updating

The first start of the candidate on mininas stopped in a loop with `SQS-C010 permissions too
open on a secrets file: master.key has mode 700`. The three datasets of the test installation
were NFSv4 datasets with inherited ACL entries (`group:builtin_users` with full access on every
file), so the secrets were readable by other local users, `chmod` could not narrow them, and
`sqsolve-init` still printed `done`. Fixed in this release: `sqsolve-init` now checks the mode it
gets and stops with `SQS-C085` (`docs/12-deployment.md`, "Permissions and ACLs"). On mininas the
ACLs were stripped from the three datasets, as that section describes, and the app started.

## Restore and reconnect with Resolve

Date: 2026-10-26. Diego, by hand: Resolve Studio 21.1.1 build 10 on Fedora Linux 44, connected to
`riatidina` on `sha-2ca757d` (11 sessions from the workstation), with the project
`2026-10-19-parto-edit` open and one of its timelines renamed between steps. The timeline name
at every step was read afterwards from the backups sqsolve took and from the database; what
Resolve did, from its log (`ResolveDebug.txt`).

| Step | sqsolve | Resolve |
|---|---|---|
| Timeline renamed `A` and saved; "Back up now"; renamed `B` and saved | Manual backup, level 1 verification passed | |
| Replace with that backup, without "Close open sessions" | The job waited for the sessions and went on seconds after Resolve was quit; done in 2 min 21 s | Started again and opened the project: timeline `A` |
| Renamed `B`, "Back up now", renamed `C`; replace with that backup, closing sessions | Done in 11 s; the restored library had `B` | No dialog. At its next save the query failed with `terminating connection due to administrator command`, Resolve reconnected within milliseconds and saved: three timeline items and a clip duration that were in neither the backup nor the database just before the replacement were written into the restored library |
| Replace with the first backup, closing sessions | Done in 10 s; the restored library had `A` | Its next save reconnected and failed with a foreign key error (`Sm2TiItem_Sm2TiTrack`); Resolve then reloaded the project on its own and showed `A` |
| Revert from the Danger zone | Done in about 8 s; the library is back to the state before the last replacement (`B`), the same rows as the backup sqsolve took of it apart from the view state Resolve saved afterwards | No reload: it kept showing `A` until the project was closed and opened again, then `B`. Its save after the reconnect wrote only view state (playhead positions) |

Reading:

- Replace and revert do what the panel says: each replacement left the library with the contents
  of the chosen backup, waiting for the sessions to close or closing them, and the revert brought
  back the state before the last replacement. Every replacement and the revert left their
  `pre_restore` backups and a single previous-state database; `sqsolve doctor` stayed without
  failures.
- With a project open, Resolve does not show that its library was replaced or reverted. It
  reconnects on its own, its next save writes what it has pending into the database now under the
  name, and only when that save fails does it reload the project. This confirms on screen the risk
  PoC-09 found through the API (`docs/poc/poc-09-forced-disconnect.md`). The replace and revert
  pages now always ask to close the project in Resolve on every workstation first; the technical
  safeguard stays in `PLAN.md` §3.
- Retention: the manual backup taken for the test expired 12 minutes later, when the scheduled
  backup ran (the library backs up every 15 minutes and keeps the last 10). Each replacement and
  the revert left two `pre_restore` backups, which are protected and also count among the last
  10, so four restores pushed the manual backup out. This matches the documented rules; it is
  recorded as a follow-up in `PLAN.md` §1.
